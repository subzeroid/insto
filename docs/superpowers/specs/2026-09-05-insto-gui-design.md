# insto-gui: самостоятельное приложение для мониторинга

Дата: 2026-09-05, Europe/Moscow.

Статус: продуктовые границы, компоновка A, самостоятельная установка и письменная спецификация согласованы пользователем. Подтверждение документа: «да», 2026-09-05. Реализация GUI ещё не начата; порядок этапов записан в [delivery map](../plans/2026-09-05-insto-gui-delivery-map.md).

## 1. Обязательный пользовательский результат

**Установил приложение → ввёл HikerAPI-токен → добавил нужные аккаунты → мониторинг работает.**

Никаких ручных установок `insto`, Python, `pip`, `uv`, настройки PATH, терминала, выбора интерпретатора, базы или plist. HikerAPI — единственный backend, предлагаемый GUI v1. Сам Python-проект `insto` сохраняет существующую поддержку других backend.

Согласованные решения:

- Отдельный проект `insto-gui`, а не новый раздел `insta-dl-gui`.
- Первая платформа — macOS. Первая продуктовая область — наблюдения, сохранённые снимки, изменения и управление фоновой службой.
- Компоновка **A**: список наблюдений слева, детали выбранного аккаунта справа; общая лента изменений — соседний раздел.
- Tauri 2 + Vue 3 + TypeScript; Python `insto` остаётся единственным владельцем доменной логики, SQLite и мониторинга.
- Приложение поставляет собственное совместимое ядро, не заменяет отдельно установленный CLI и не меняет существующие данные без подтверждения.
- Закрытие окна или выход из GUI не останавливает включённую фоновую службу. Автозапуск — после входа пользователя в macOS, не до логина.
- Проектирование, реализация и ревью `insto-gui` выполняются на Astra. Sol-агенты, использованные для предыдущей работы над сервисом, к GUI не привлекаются.

Установка не выбирает наблюдаемые аккаунты за пользователя. После ввода токена единственный обязательный предметный ввод — имя аккаунта при добавлении наблюдения.

## 2. Что переиспользуется, что действительно отсутствует

Основа — `insto` на `6d2dfd0` из `feat/macos-watch-service`, поверх релиза 0.7.20. Эта ветка ещё не слита и не опубликована. Документационная ветка не выдаёт будущие возможности за доступные в PyPI.

Уже есть:

- macOS controller `watch_service.py`, безопасные install/status/uninstall и защищённый manifest;
- `watch_service_runner.py`, который загружает конфигурацию и вызывает существующий daemon;
- один executor на канонический путь базы, устойчивые регистрации, двухсекундная сверка SQLite, восстановление после сбоев;
- схема SQLite v2, снимки по `target_pk`, активные/приостановленные регистрации по username;
- фильтрация секретов, защищённые файлы, ротация логов, HikerAPI backend и типизированные ошибки;
- чтение списка наблюдений через отдельное read-only соединение.

Нужно добавить в `insto`, не дублировать в Rust:

- ограниченный версионированный desktop JSON-интерфейс;
- строгую проверку HikerAPI-токена: `refresh_quota()` сейчас подавляет ошибки и для onboarding непригоден;
- read-only перечисление сохранённых снимков и их сравнение: текущий `/diff` обращается к API, `/history` показывает историю команд;
- безопасные операции изменения интервала и pause/resume с защитой от устаревшего состояния;
- небольшие операции setup/recovery для GUI с сохранением текущих правил сервиса.

В `insta-dl-gui` переиспользуются визуальные принципы, организация Vue/IPC и опыт сборки. Его самостоятельный Rust-клиент HikerAPI, downloader и media-catalog в новый проект не переносятся.

## 3. Установка и поставка ядра

### Выбранный вариант

В приложение включается **переносимый CPython + установленный wheel `insto` + зафиксированные runtime-зависимости**. Это не editable checkout и не виртуальная среда, скопированная с машины разработчика.

Рекомендуемая база — `python-build-standalone`, обычная GIL-сборка CPython 3.12. При реализации packaging фиксируются точная поддерживаемая patch-версия, upstream build, архитектура, SHA-256 и hashes всех wheels. Runtime не включает dev/docs-зависимости или необязательный aiograpi.

Tauri включает подготовленное дерево runtime через bundle resources. На первом запуске Rust-часть автоматически публикует проверенную копию в постоянный приватный каталог:

```text
~/Library/Application Support/insto-gui/
  runtimes/<build-id>/python/       # неизменяемый runtime конкретной сборки
  profile/                         # INSTO_HOME приложения по умолчанию
    config.toml                    # только после проверки токена
    store.db
    output/
    services/watch/                # manifest, management.lock, rotating logs
  desktop-state.json               # версии, профиль, желаемое состояние службы; без токенов
```

`build-id` определяется содержимым и архитектурой, а не строкой из пользовательского ввода. GUI не создаёт команду `insto` в системном PATH, не запускает shell bootstrap, `pip install`, Homebrew или сетевое скачивание runtime на машине пользователя. Интернет нужен для HikerAPI, но не для подготовки уже поставленного ядра.

Публикация runtime сериализована отдельной межпроцессной блокировкой: проверка manifest → приватный временный каталог внутри managed root → проверка каждого файла → локальный handshake → атомарная публикация. Нельзя перезаписывать уже запущенную версию. Отказ, прерывание и нехватка места оставляют предыдущую версию работоспособной. Частичный каталог не считается готовым.

Проверяются владелец, типы файлов и допустимые пути. Допустимы только объявленные внутренние относительные symlink, которые после полного разрешения остаются внутри runtime; внешние ссылки, traversal, FIFO и устройства запрещены. Содержимое сверяется с manifest доверенного app bundle, а не с manifest из изменяемого каталога назначения. Исполняемые права сохраняются; родительские каталоги приватные. Hash не заменяет подпись издателя.

Запуск ядра: фиксированный абсолютный `<runtime>/python/bin/python3 -I -B -m insto.desktop`. Запуск службы сохраняет существующую модель Python module entrypoint; для поставляемого runtime controller должен формировать `python -I -B -m insto.service.watch_service_runner <manifest>`. Добавление `-B` к текущему service-контракту проверяется вместе с manifest/plist compatibility: ни bridge, ни daemon не должны создавать bytecode cache внутри проверенного runtime. Поэтому не требуется изображать frozen-приложение Python-интерпретатором.

### Рассмотренные альтернативы

- GUI поверх установленного пользователем CLI: меньше packaging, но отвергнуто пользователем как обязательный путь первого запуска.
- PyInstaller sidecar: допустим технически, но потребовал бы отдельного frozen entrypoint и изменения текущего контракта запуска службы. Не основной путь v1.
- Rust-переписывание ядра: создаёт отдельные backend, SQLite-правила и scheduler. Вне границ проекта.

### Релизные ограничения

Для macOS подготавливаются отдельные arm64 и x86_64 артефакты, каждый со своим runtime. Минимальная версия ОС должна совпадать у Rust-приложения, CPython и всех native wheels; окончательная build matrix фиксируется packaging-планом по реально проверенным артефактам, а не предположением о поддержке.

Публичный сценарий «установил и запустил без обхода защиты» требует Developer ID signing, notarization и проверки скачанного DMG с quarantine на чистом Mac. Проверяются также подписи вложенных исполняемых файлов после копирования runtime. Ad-hoc сборка пригодна для разработки, но не является выполнением этого релизного критерия. Покупка сертификатов, использование ключей и публикация требуют отдельной авторизации.

Порядок production-сборки: установка wheels → подпись вложенных исполняемых файлов и библиотек → окончательный runtime manifest и `build-id` → подпись внешнего app bundle → notarization/stapling → проверка скачанного DMG и скопированного runtime. Подпись меняет байты исполняемых файлов, поэтому unsigned manifest из P0 нельзя использовать после signing. После вычисления окончательного manifest runtime не изменяется и не подписывается повторно. Подпись выполняется изнутри наружу; это соответствует [правилам Apple для nested code](https://developer.apple.com/library/archive/technotes/tn2206/_index.html).

## 4. Первый запуск: один экран токена

На фоне подготовки runtime показывается короткий статус, без выбора технических параметров. После подготовки — поле HikerAPI-токена, показать/скрыть ввод, ссылка на получение токена и кнопка **«Подключить и начать»**.

Под кнопкой коротко объясняется: приложение включит локальную фоновую службу, будет работать после закрытия окна и расходовать HikerAPI-лимит при проверке добавленных аккаунтов. Это действие включает службу; отдельный вопрос про launchd или plist не нужен. macOS может показать собственное уведомление о фоновом элементе.

Последовательность:

```text
Подготовка ядра → Ввод токена → Проверка доступа
  → Защищённое сохранение → Создание локальной базы
  → Регистрация службы → Проверка запуска → Наблюдения
```

Проверка токена выполняется в Python через существующий HikerAPI transport и error taxonomy. Нужен строгий вызов balance/auth-проверки с раздельными результатами: действителен, отклонён, исчерпана квота, временная ошибка, неизвестный ответ. Нельзя трактовать «неизвестная квота» как подтверждение токена или менять мягкое поведение баланса в REPL. Токен регистрируется в redactor до потенциально ошибочного запроса.

Недействительный токен не заменяет рабочий и не сохраняется как завершённая настройка. Сетевой сбой позволяет повторить проверку, не обвиняя токен. Нулевая квота объясняется отдельно: доступ настроен, новые проверки невозможны до пополнения; это не зелёное состояние работающего мониторинга.

Успешно проверенный токен записывается атомарно в owner-only `profile/config.toml`, директория 0700, файл 0600. Ни Rust state, ни frontend storage, URL, аргументы процесса, plist или runtime manifest не содержат его. Секрет передаётся дочернему процессу через stdin и после операции удаляется из frontend state; не обещается гарантированное обнуление памяти JS.

Если после сохранения токена не запустилась служба, настройка сохраняется. Экран предлагает исправление/повтор запуска, не требует заново вводить токен и не показывает ложное «всё работает». После аварийного закрытия GUI первый запуск продолжается из наблюдаемого состояния, а не слепо повторяет все записи.

### Замена токена после настройки

Работающий daemon загружает конфигурацию один раз при старте: запись нового файла сама по себе не меняет его credential. `credentials.replace` сначала проверяет новый токен, затем сериализует изменение с остальными операциями профиля и службы. Для своей работающей службы: сохранить защищённую предыдущую конфигурацию → подтвердить остановку → атомарно записать новую → запустить → проверить новый запуск. Если служба намеренно остановлена, она остаётся остановленной; UI сообщает, что токен сохранён для следующего запуска.

При неудаче запуска восстановить прежнюю конфигурацию и прежнее желаемое состояние, повторно запуская только ранее работавшую собственную службу. Если rollback не удался, показать отдельное состояние восстановления, не успех. Если остановку подтвердить нельзя, новый токен не записывать. Перезапуск подтверждает загрузку конфигурации, но не успешную проверку аккаунтов: её UI показывает только по фактическим результатам daemon. Общий бюджет составной операции — 120 секунд, включая rollback; после исчерпания бюджета результат перечитывается, а не повторяется вслепую.

До первого изменения на диске нужен owner-only recovery record в профиле: стадия, прежнее желаемое состояние и ссылка на защищённую резервную конфигурацию. Токен не дублируется в несекретном desktop state. После crash следующий запуск продолжает восстановление до новых изменений; резервная конфигурация удаляется после завершённого применения или rollback. Для внешней CLI-службы замена заблокирована до явного принятия управления: нельзя сообщать, что токен применён, оставив внешний daemon на старом credential.

В пустом состоянии основное действие — **«Добавить аккаунт»**. Для первого наблюдения достаточно username; начальный интервал — существующие 300 секунд. Рядом видны интервал и предупреждение о расходе запросов. Регистрация сама не делает пробный профильный запрос: первый настоящий снимок собирает daemon, UI показывает «Ожидает первой проверки».

## 5. Границы процессов и JSON-контракт

```text
Vue: экран, ввод, отображение состояний
  ↓ узкий Tauri invoke с типизированными аргументами
Rust: доверенные пути, публикация runtime, процессы, ограничения ввода/вывода
  ↓ JSON через stdin/stdout, без shell и TCP-порта
Python insto.desktop: проверка протокола, доменные операции, безопасные DTO
  ├─ read-only SQLite: состояния и сравнения сохранённых снимков
  ├─ короткая транзакция: добавить/изменить/приостановить/удалить наблюдение
  └─ существующий service controller: управляемая регистрация launchd

launchd → постоянный Python runtime → существующий daemon → HikerAPI / SQLite
```

На операцию создаётся короткоживущий bridge-процесс; он не является вторым daemon. Базовые режимы не импортируют provider SDK и не открывают `open_runtime()`, поскольку тот создаёт backend и изменяемый HistoryStore. Для чтения используется отдельный read-only путь; для изменений — минимальный store lifecycle в Python.

Протокол v1: один UTF-8 JSON request на строке, один JSON response и exit. Envelope содержит `protocol_version`, `request_id`, `operation`, `params`; ответ — тот же request ID и либо `result`, либо безопасный `error {code, message, retryable}`. Произвольные module names, команды shell, SQL и пути runtime не принимаются. stdout содержит только protocol output; сторонний stderr ограничивается и не пробрасывается как пользовательское сообщение.

Ограничения: вход до 64 KiB, ответ до 2 MiB, stderr до 64 KiB. Таймаут чтения — 10 секунд, проверки токена — 30 секунд, локального изменения watch — 10 секунд, составной операции службы — 120 секунд, подготовки runtime — 120 секунд. Внутренние native subprocess сохраняют лимит 10 секунд каждый. Не более двух одновременных чтений и одной изменяющей операции на выбранный профиль. GUI не выдаёт неполный JSON за успех. После разрыва связи с изменением показывает «результат неизвестен» и перечитывает состояние вместо автоматического повторения неидемпотентной команды.

Обычное закрытие GUI прекращает чтения, но дожидается начатых локальных изменений в пределах их бюджета. Внешняя отмена не должна отпускать management lock, пока `launchctl` ещё выполняется; используется уже исправленный drain-контракт сервиса. Авария GUI/bridge проверяется отдельными тестами восстановления. Служба не дочерний процесс GUI и не завершается вместе с ним.

Минимальные группы операций:

| Группа | Назначение | Сеть |
| --- | --- | --- |
| `hello` | Версии протокола/ядра/схемы, capabilities, ограничения | Нет |
| `setup.inspect`, `setup.configure` | Состояние настройки, проверка и сохранение токена | Только явная проверка токена |
| `overview`, `watches.list` | Служба и регистрации | Нет |
| `watches.add`, `update`, `pause`, `resume`, `remove` | Изменение регистраций через доменный слой | Нет |
| `snapshots.targets`, `list`, `compare`, `changes.list` | Только сохранённые данные | Нет |
| `service.start`, `stop`, `repair` | Служба выбранного профиля | Нет прямых запросов; запущенный daemon проверяет аккаунты |
| `settings.inspect`, `credentials.replace` | Несекретные настройки, явная замена токена | Только проверка нового токена |

Имена уточняются в реализации только совместно с контрактными тестами. GUI использует согласованную protocol major version; несовместимость отключает операции с объяснением, а не пытается разбирать текст CLI. Пути профиля выбирает Rust из зарегистрированного local state; webview не получает произвольный filesystem/shell доступ.

Bridge и service получают очищенное app/provider/proxy/Python environment. В macOS production не наследуются `DYLD_*`, пользовательские import paths, shell-only токены или произвольные proxy/CA overrides. Явные сетевые настройки читаются из защищённого профиля. Provider отсутствует в Rust и браузере.

## 6. Наблюдения и согласованность

Сохраняются глобальный предел **3 активных наблюдения на базу**, минимальный интервал **300 секунд**, существующие retry/backoff, автоматическая пауза, расписание и executor lock. GUI не увеличивает лимиты и не запускает дополнительный цикл.

Список содержит username, active/paused, интервал, время последней успешной проверки, ожидание первой проверки и безопасный признак ошибки. Состояние процесса службы не подменяет состояние каждого наблюдения. Произвольный сохранённый `last_error` не отдаётся frontend: старые секреты нельзя безопасно редактировать без их знания.

Добавление, изменение интервала, pause/resume и удаление проходят в транзакции с проверкой ревизии регистрации. Desktop DTO выдаёт непрозрачную ревизию, вычисленную из identity/status/interval, без раскрытия внутреннего `registration_id`. Устаревшая команда получает conflict и перечитывает строку. Служебные обновления `last_ok` не делают эту ревизию устаревшей сами по себе.

При изменении интервала/паузе/возобновлении пересоздаётся generation регистрации там, где нужно отсечь результаты старого tick. Проверка лимита и изменение состояния атомарны. Нельзя реализовать update как delete+add: это создаёт промежуточную потерю регистрации и гонку за свободным слотом. Существующие CLI semantics сохраняются.

В обычном случае daemon подхватывает изменение на очередной сверке. UI сначала подтверждает сохранение команды, затем показывает фактическое состояние, не обещая мгновенного завершения уже начатого HTTP-запроса. Уже полученный снимок может успеть сохраниться до подхвата паузы; пауза не откатывает зафиксированные данные. Удаление регистрации требует подтверждения и сохраняет исторические снимки.

Просмотр обновляет локальный overview каждые 5 секунд, пока окно видно, и после действий. На скрытом окне polling прекращается; при возвращении выполняется одно обновление. Это чтение SQLite, не повторный запрос HikerAPI. Ошибка обновления сохраняет последние данные с отметкой «устарели» и временем последнего успешного чтения.

## 7. Снимки, идентичность и лента изменений

Основной экран соответствует выбранному A. Выбор строки не вызывает сеть. Справа — доступные снимки, выбор пары и сравнение отслеживаемых полей. Без снимков — «Ожидает первой успешной проверки»; с одним — «Первый снимок», а не «ничего не изменилось».

Общая лента строится из сравнения соседних сохранённых снимков одного `target_pk`, не из логов и не из нового event store. Отслеживаемые profile fields и avatar/banner hash semantics переиспользуются из `insto`. Первый снимок — baseline, а не набор изменений из `null`. Для поля, отсутствующего в старом формате снимка, показывается «неизвестно», а не выдуманное удаление.

ID снимка — существующий SQLite `id`; порядок — `(captured_at, id)`, с UTC timestamps в протоколе и местным временем в UI. Пара снимков должна принадлежать одному `target_pk`; отсутствующий после retention снимок даёт понятный результат «больше не доступен» и обновление списка.

Username изменяемый. Регистрация по username и сохранённый `target_pk` не объявляются одной идентичностью без оснований. Read-only поиск возвращает **исторические** соответствия username в снимках: ноль — истории ещё нет, одно — показывается PK и дата сохранённых данных, несколько — пользователь выбирает историю по PK. Нельзя молча выбирать «самый свежий» аккаунт при переиспользовании username. Сравнение всегда внутри одного PK, автоматического переноса наблюдения на другой username нет.

Лента помечается как сравнение локальных наблюдений между двумя временами, не как точное время действия в Instagram. Число подписчиков не раскрывает список конкретных новых подписчиков. Новые медиафайлы не скачиваются ради предпросмотра; используются инициалы и текст, потому что снимки сейчас сохраняют hash аватара, а не его историческое изображение.

Действует текущее хранение: **до 30 дней и не более 100 снимков на аккаунт**; ограничение по количеству может сократить фактический период. Ни «вечная история», ни полный архив событий не обещаются. GUI не отключает prune и не создаёт собственную копию истории.

Чтения используют read-only транзакции и проверку schema version без mkdir/chmod/migration. Пагинация не более 50 отображаемых элементов. Лента проверяет максимум 200 кандидатов за запрос и возвращает cursor продолжения даже при пустой странице изменений; predecessor ищется в пределах того же PK. Поиск исторических соответствий username просматривает не более 2 000 строк за запрос и возвращает признак неполного результата: до конца поиска единственность PK не утверждается. На один сырой снимок допускается до 64 KiB JSON; превышение даёт безопасный диагностический результат. Действуют общий лимит ответа и таймаут чтения, включая SQLite busy timeout в одну секунду. Повреждённый JSON, future schema и неоднозначное соответствие — явные состояния, не пустой успешный результат. Инженерный план проверяет эти бюджеты на большой fixture базе.

Уточнение read-only согласовано пользователем 2026-09-05 после независимой консультации Claude Fable 5.1 / xhigh и проверки Astra: **операции чтения C2 не изменяют логические данные, схему и настройки, но SQLite разрешено штатно обслуживать собственные WAL/SHM-файлы**. Прикладной код чтения не создаёт профиль или блокировки, не выполняет chmod, миграцию, запись SQL, удаление/переименование файлов, сетевые запросы или изменение службы. Проверяются доверенные пути, владелец и типы файлов; соединение использует `mode=ro`, `query_only` и одну короткую read-транзакцию. Побайтовая неизменность sidecar-файлов не обещается. WAL может содержать уже подтверждённые данные: приложение не удаляет и не игнорирует его. Отсутствующий профиль не инициализируется; наличие WAL/SHM не используется как признак работающего daemon.

Проверка неизменности основного файла выполняется без конкурентного writer. В тестах с daemon проверяются отсутствие записей со стороны читателя, видимость подтверждённых WAL-данных, согласованность одной read-транзакции и освобождение её при завершении/таймауте. Существующие строгая проверка `check_database` и тесты C1 не ослабляются: C2 получает отдельный ограниченный путь чтения и не копирует всю базу при обновлении overview или страницы истории.

Лимит строк не разрешает материализовать все их JSON сразу: 2 000 × 64 KiB ≈ 125 MiB до Python-объектов. Чтение потоковое, пакет не более 16 сырых снимков; oversized payload отсекается SQL-проекцией по byte length до передачи JSON в Python. Истёкший бюджет прерывает SQLite через progress handler и возвращает безопасный timeout, а не неполную успешную страницу. Пятиисекундный overview не пересчитывает историю; поиск и сравнение выполняются по действиям пользователя. Индексы добавляются только после `EXPLAIN QUERY PLAN` на большой fixture, без новой схемы ради предполагаемой оптимизации.

## 8. Служба, обновления и восстановление

В GUI четыре раздела: **Наблюдения**, **Изменения**, **Служба**, **Настройки**. Экран службы раздельно показывает: зарегистрирована ли она, наблюдаемый process state, доступно ли ядро/база, успешны ли проверки аккаунтов. Для `launchctl print` неизвестный формат остаётся unknown, а не интерпретируется как здоровье.

После успешного onboarding желаемое состояние managed-службы — running. Повторный запуск GUI не дублирует регистрацию и не перезапускает исправный watcher. «Остановить» отключает именно принадлежащую приложению службу с сохранением данных; повторный запуск GUI уважает остановку. «Запустить» и явное «Восстановить» запускают точную принадлежащую приложению регистрацию, включая случай loaded-but-cleanly-exited. Нужное расширение controller добавляется в Python с ownership/lock проверками; Rust не реализует собственный `launchctl` controller и не сигналит по PID из диагностического текста.

Постоянный runtime path не зависит от DMG, текущего каталога или нахождения `.app` в прежней папке. Работа после закрытия окна проверяется не только по регистрации, но и новым tick в SQLite. Сон, logout, отсутствие интернета, исчерпанный лимит и запрет background item со стороны macOS честно показываются как ограничения, а не обещание 24/7 на спящем ноутбуке.

Обновления v1 распространяются новым приложением, без отдельного сетевого auto-updater. Новый runtime сначала проверяется, затем приложение сериализованно переводит только **свою** включённую службу на новую версию. Предыдущий runtime, точные manifest/config и желаемое состояние сохраняются до подтверждения запуска. Неуспех означает явную ошибку и восстановление старого запуска, а не удаление обоих вариантов. Остановленная пользователем служба не включается из-за обновления.

Первая версия GUI не требует изменения SQLite schema v2. Future schema блокирует запись. Любые будущие изменения схемы потребуют отдельного migration/backup плана; нельзя обещать откат старого runtime поверх уже несовместимой базы. Совместимый Python CLI не переустанавливается и не обновляется из GUI.

В настройках есть действие отключения фоновой службы перед удалением приложения. Оно не удаляет историю, token file или чужую установку. Перенос `.app` в корзину сам по себе не является деинсталлятором постоянно установленной службы; это объясняется явно. Очистка старых runtime не выполняется рекурсивно по общему каталогу и не является обязательной автоматикой v1.

### Существующая установка insto

По умолчанию новый GUI использует собственный `profile/`; `~/.insto` не читается и не мигрируется в onboarding. В дополнительных настройках можно выбрать существующий HikerAPI home и явно подтвердить подключение к той же базе, без копирования истории и секретов.

Сначала выполняется read-only проверка схемы, путей и существующего service manifest. Если работает внешняя CLI-служба, GUI может показывать и изменять регистрации через совместимое ядро, но не заменяет её interpreter, регистрацию или настройки автоматически. Lifecycle-команды требуют отдельного явного принятия управления с проверкой ownership и rollback. При неясном владельце — только чтение, без убийства процесса. Одновременно управляется один выбранный профиль. Перед переключением показывается, какая прежняя managed-служба будет остановлена; переключение происходит только после подтверждения. Внешняя CLI-служба прежнего профиля не останавливается, её независимая работа объясняется отдельно.

Существующий aiograpi home не переключается на HikerAPI автоматически: GUI сообщает, что этот backend пока не поддерживается его first-run продуктовым сценарием. Ввод нового токена, proxy и смена профиля доступны в настройках, но не усложняют обычный первый запуск.

## 9. Ошибки и безопасность интерфейса

- Все тексты из Instagram и базы отображаются как текст, не HTML; URL не выполняются и не открываются автоматически.
- IPC capabilities ограничены локальным окном и конкретными командами. У webview нет универсального filesystem, shell или сетевого клиентского доступа к HikerAPI.
- Ошибки авторизации, сети, квоты, schema mismatch, повреждённого runtime и service ownership имеют разные безопасные коды. UI не просит открыть терминал как штатный способ завершить настройку.
- Токены, proxy credentials и исторические произвольные ошибки не попадают в logs, protocol traces, crash reports, DOM после сохранения или browser storage. Телеметрии и внешней отправки диагностик нет.
- Права на файлы — защита от других пользователей, не обещание шифрования диска или защиты от вредоносного процесса того же пользователя.
- Нет фонового сбора Instagram до явного подключения токена и добавления аккаунта. Нет скрытой проверки произвольного тестового аккаунта.

## 10. Порядок разработки и критерии готовности

Проект имеет два связанных deliverable: расширение ядра в `insto` и самостоятельный desktop в `insto-gui`. Для них составляются отдельные implementation plans, связанные одним protocol contract. Текущая документационная ветка не смешивает GUI с уже готовой веткой LaunchAgent.

1. **C0 → P0:** foundation ядра и developer proof переносимого runtime, TLS/SQLite/SDK imports и изолированной fake-службы. Это ещё не app.
2. **C1 → P1 → C2:** сначала setup, замена токена и service recovery; затем настоящий минимальный app с автоматической публикацией runtime и новым tick после выхода; затем read-only history и revision-safe watches. На чистом Mac проверяется отсутствие зависимости от внешних Python/CLI. Если app packaging/signing не подтверждены, полный UI не строится на неподтверждённой упаковке. Текущие CLI и daemon suites сохраняются.
3. **GUI A:** token-only onboarding, список/детали, лента, служба, настройки; mock IPC для frontend tests и визуальной проверки, настоящий bridge для integration.
4. **Установка и восстановление:** повторный запуск, обновление runtime, interruption, внешний CLI, реальные launchd lifecycle и удаление службы с сохранением данных.
5. **Релизная проверка:** signed/notarized downloaded DMG на заявленных архитектурах/ОС; не подменять установленное приложение запуском из checkout. До этого продукт не называется готовым к беспрепятственной установке.

Обязательные acceptance проверки:

- Чистая учётная запись: нет Python, `insto`, `uv`, `pip` или developer PATH. После установки единственный обязательный экран настройки — токен.
- Подготовка runtime не требует сети. Фальшивый/повреждённый payload, неправильная архитектура, внешняя symlink, чужой каталог и нехватка места дают безопасный отказ без порчи рабочего runtime.
- Подтверждённый токен → сервис работает → аккаунт добавлен → сохранён первый снимок → закрыт GUI → следующий tick появляется. Первый baseline не изображается как изменение.
- Неверный токен, zero quota, timeout, invalid provider schema и заблокированная сеть различаются. Неуспешная замена токена не уничтожает действующий.
- Статус, выбор аккаунта, сравнение снимков и листание ленты не вызывают provider API и не изменяют базу.
- Три активных наблюдения, гонка двух добавлений за последний слот, stale revision, pause во время tick, resume и сохранность истории после удаления регистрации.
- Равные captured_at, разные PK с одним username, rename, отсутствующее поле старого снимка, повреждённый JSON, retention между списком и compare, большой объём данных и ограниченные ответы.
- Повторное открытие не создаёт второй executor; stop сохраняется; clean exit loaded job можно восстановить; crash перезапускается; отмена management-команды не освобождает lock преждевременно.
- Обновление и авария между его этапами восстанавливаются без удаления старого runtime/данных. Перемещение app и размонтирование DMG не ломают зарегистрированный путь ядра.
- Подключение существующего home не меняет его schema/config/службу до подтверждённого соответствующего действия.
- Проверки секретов охватывают stdout/stderr, runtime metadata, plist, журналы и frontend state. Интерфейс проверяется мышью и клавиатурой, включая loading/empty/error/stale состояния.

Offline/fake тесты не используют настоящий токен пользователя. Provider smoke перед релизом выполняется отдельно с явным тестовым credential и бюджетом запросов. Зелёный unit suite не заменяет проверку конечного app bundle.

## 11. За пределами первой версии

Windows/Linux, мобильный GUI, remote server, HTTP API, облачная синхронизация, второй scheduler, Rust backend, полный набор OSINT-экранов, медиабиблиотека/скачивание, новые уведомительные каналы, увеличение watch limits, вечная история, aiograpi onboarding, автоматический сетевой updater, автоматическое удаление всех пользовательских данных.

Проектирование не разрешает установку службы на живые наблюдения пользователя, изменение sibling repositories, публикацию GitHub/PyPI, мерж готовой ветки сервиса или использование signing credentials без соответствующего запроса.
